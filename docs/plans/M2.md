## Goal

The phone is a fast, steady marker sensor: the highest frame rate its camera sustains at a short exposure,
detection in C++ with ROI tracking, frames over UDP (tether or Wi-Fi) or TCP (adb reverse), measured end to
end, held for hours without Android throttling it unpredictably. The server gains the TCP transport,
`adb reverse`, `/api/beacon`, previews and benchmark storage.

## Prerequisites (owner, once)

- Android SDK: install **NDK (Side by side)** and **CMake** in Android Studio → SDK Manager → SDK Tools
  (not installed on 2026-10-01). Record the versions in `android/app/build.gradle.kts` (`ndkVersion`).
- On the phone: USB debugging on; allow the app's camera and notification permissions; battery optimisation
  exemption; realme "App battery management" → allow background activity (the app shows these steps).

## Architecture (app)

```
MainActivity (Views)  ── start/stop, mode WIRED/WIRELESS, pair code, stats, benchmark UI, dim "demo" screen
   │ binds
SensorService (foreground, type camera) ── owns everything below; wake lock; Wi-Fi low-latency lock
   ├─ CameraController   Camera2: open, one YUV ImageReader, manual exposure/ISO/frame duration, AF/AWB lock,
   │                     capabilities report (D30); applies settings and thermal levels
   ├─ FramePipeline      Image → JNI nativeProcess(yBuffer, stride, w, h, capNs, …) → result buffer (D31)
   │    └─ native (C++): RoiTracker (prediction, windows, lost → full scan), Detector (cv::aruco on Mat views,
   │                     thread pool on the fastest cores), result packing; zero per-frame allocation
   ├─ FrameSender        builds the §2 JSON into a reused byte buffer; UDP socket or TCP framing (§2.1);
   │                     queue depth 1; answers sync (§3) on the same socket
   ├─ Discovery          §4.1/§4.2: beacon listener bound to the chosen interface; adb probe; manual host
   ├─ Session            §4.3: WebSocket (OkHttp), hello/welcome/settings/status/bench, token storage
   ├─ ClockSource        §3.1 sync-clock detection
   ├─ PerfManager        sustained mode, ADPF hint session, CPU load, core frequencies (D34)
   ├─ ThermalGovernor    headroom/status → ladder level → CameraController (D34)
   ├─ PreviewEncoder     downscaled Y → greyscale JPEG at preview.fps, off the tracking threads (§4.6)
   ├─ Stats              per-stage timings (ring buffers, percentiles without allocation)
   └─ Benchmark          runs the §4.7 matrix, reports `bench`
```

## Steps (outline; the final plan will add file lists, interfaces and tests per step)

1. **Native build and OpenCV.** Add the C++ module (CMake, `ndkVersion`, `abiFilters arm64-v8a`), OpenCV via
   the Maven AAR and Prefab (fallback per D31). A JNI smoke test returns OpenCV's version and detects a marker in
   a bundled test image (instrumented test on the phone). Check that `assembleDebug` still builds on this laptop.
2. **Camera2 controller.** Enumerate the back camera's capabilities (everything in `hello.camera`); open one
   YUV `ImageReader` (`maxImages` 3) at the requested size; AE off with exposure/ISO/frame duration; AF once then
   lock, AWB once then lock; fps 0 = max from `getOutputMinFrameDuration`; `setup` mode adds a small preview
   surface for aiming, removed in `tracking`. Fallback without `MANUAL_SENSOR`: AE lock at minimum exposure
   compensation, reported. Log every frame's `SENSOR_TIMESTAMP`, exposure and rolling-shutter skew.
3. **Zero-copy pipeline.** Direct Y-plane buffer + row stride → one JNI call; native side wraps with `cv::Mat`
   (no copy), all buffers preallocated; results into a preallocated direct buffer; the `Image` is closed right after.
   Verify "no per-frame allocation": Android Studio memory profiler over 5 minutes shows no GC caused by the
   pipeline (record the screenshot/numbers in Results).
4. **ROI tracking (D32).** Constant-velocity prediction to the new capture time, windows per `settings.tracking`,
   lost → full scan next frame, full scan every N, moving untracked tags promoted to tracked; windows processed in
   parallel on the fastest cores (`threads`); frames carry `scan`/`searched`. Unit tests in C++ (GoogleTest or a
   small test runner) on synthetic images: a tag moving 300 px/s is kept in its window; a lost tag triggers a full
   scan; windows at the image edge are clipped.
5. **Transport and discovery (D33).** WIRED: tether beacon (3 s) → adb probe → retry every 5 s; WIRELESS: Wi-Fi
   beacon; sockets bound to the chosen network; low-latency Wi-Fi lock; UDP sender and TCP framing (§2.1) with
   depth-1 queues; sync replies on the frames socket; mode switch ends the session. Server side: TCP frames
   listener (`tcp.frames_port`), `wired.adb_reverse` runner, `GET /api/beacon`; the simulator phone gains
   `transport = "tcp"` so the TCP path is tested end to end on the laptop.
6. **Session and clock (§3.1, §4.3).** Pairing screen, token storage (EncryptedSharedPreferences), hello with
   capabilities, settings application, status at 1 Hz with every §4.5 field (`null` where not measurable).
7. **Performance and thermal (D34).** Foreground service with notification; partial wake lock; keep screen on +
   dim demo screen; sustained performance mode where supported; ADPF hint session (API 31+) on the detection
   threads with per-frame actual durations; battery-optimisation request and realme instructions; thermal
   governor with the ladder and hysteresis from `settings.thermal`, reporting level/reason/headroom.
8. **On-screen stats and preview.** fps vs target, per-stage p50/p95 (pipeline, detect full/roi, send,
   cap→sent), CPU %, current max core frequency, thermal status/headroom/level, link mode and state, markers
   seen; greyscale JPEG preview (§4.6). Server: `GET /api/cameras/{cam}/preview.jpg`, dashboard preview panel.
9. **Benchmark mode (D36, §4.7).** Matrix over resolution (from `yuv_sizes`, same aspect ratio), fps (max, 60, 30),
   pipeline (`native_roi`, `native_full`, `java_full` baseline via the OpenCV Java API), `full_scan_every`
   (5, 10, 20); 30 s each; `app_mode = benchmark` throughout; results table on screen and `bench` to the server.
   Server: store runs (`benchmarks` table in `state.db`), `GET /api/cameras/{cam}/benchmarks`, dashboard table,
   and "apply these settings" (writes `PUT /api/camera-settings`).
10. **Docs and results.** README (NDK/CMake, install, pairing, the three modes, realme battery settings);
    Results; Proposed changes.
